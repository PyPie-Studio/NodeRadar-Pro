🔒 Fix hardcoded database password vulnerability using DPAPI

🎯 What:
The application hardcoded the LiteDB database encryption password (`PyPie-NR-Pro-Sec-2026`) directly in the source code (`Data/LocalDatabase.cs`). This vulnerability nullified the intended local data encryption, as the key could be trivially extracted from the binary.

⚠️ Risk:
A compromised host machine or a malicious actor who extracts the binary could trivially access sensitive, supposedly AES-256 encrypted, data in the user's `noderadar.db` file (such as network asset discovery, device telemetry, and logs) by simply reading the hardcoded password.

🛡️ Solution:
- Added `System.Security.Cryptography.ProtectedData` to leverage the Windows Data Protection API (DPAPI).
- Modified `LocalDatabase.cs` to generate a secure, random 32-byte password if one does not exist.
- Used `ProtectedData.Protect` (DPAPI) bound to the `DataProtectionScope.CurrentUser` to encrypt this random password and store it locally as `db_key.bin` next to the database file.
- Introduced a backward-compatible migration process `MigrateDatabase()`: when opening an existing database without a DPAPI key, the app attempts to connect using the legacy hardcoded password, dynamically copies all data to a new LiteDB instance encrypted with the newly generated DPAPI password, and replaces the old file, ensuring a seamless and fully-secure user experience moving forward.
